## Update (later still same day): Step 15 — OpenLane GDS flow for gpu_top DONE

Ran the full OpenLane2/sky130A hardening flow on `gpu_top.sv` (dispatcher + 4×
`dda_core` + collector + MMIO), 20 MHz/50ns target. Full writeup:
`docs/decisions/gpu_top_gds.md`. Short version:

- Found and fixed two real Yosys-incompatibilities in existing (already
  hardware-verified) RTL: `return` statements in `dda_core.sv`'s
  `dist_to_ascii()` function (Yosys doesn't support `return` in functions at
  all), and the `$sin`/`$cos`/`$atan2` LUT-table generation in an `initial`
  block (not synthesizable — Vivado tolerates it, Yosys doesn't implement
  these system functions for synthesis). Fixed the LUTs by freezing the
  already-verified values into `$readmemh`-loaded hex files
  (`rtl/gpu/luts/*.hex`, captured bit-exact via a temporary `$writememh` dump,
  not recomputed from scratch) — same idiom as `map.hex`/`font8x8.hex`
  elsewhere in the project.
- Found and fixed a structural issue: Yosys hard-rejects unpacked-dimension
  module ports. Flattened the per-core array ports on `gpu_dispatcher.sv`,
  `gpu_collector.sv`, and `gpu_top.sv` (and updated `soc_top.sv`'s wiring to
  match, since it instantiates the same `gpu_top.sv`) into packed
  bit-sliced buses. Purely representational — verified via the full sim
  regression, still 80/80 + 80/80 PASS, same cycle count, no new lint warnings.
- **Result: timing closes with +12.48ns worst setup margin across all 10 PVT
  corners (0 setup/hold violations), Magic DRC + KLayout DRC + Netgen LVS all
  PASS, GDSII generated** (`gpu_top.gds`, 263 MB, ~1.72mm × 1.72mm die,
  30.4% utilization).
- Known follow-up, non-blocking: antenna violations (215 pin/192 net) and max
  slew/cap warnings in all corners — standard DFM polish, not correctness
  bugs, not yet addressed.

## Update (later same day): dda_core.sv timing fix

The previous handoff below flagged WNS at a razor-thin +0.020ns and asked for the real
critical path to be identified with `report_timing` before touching GPU logic again — and
guessed it was probably `gpu_collector.sv`'s row mux or `wall_top`/`wall_height` fanout. That
guess was wrong. Read the actual timing report and found the real critical path inside
`dda_core.sv`'s per-column ray-direction setup (`player_idx` → sin_table lookup → DSP48E1
multiply → subtract → abs/compare/mux, all landing on `ddx`/`ddy` in one cycle, 17 logic
levels, 15.23ns) — pre-existing logic, not something the wall-height work added, that had
apparently always been the tightest path in the design.

**Fix:** added a `DIR_WAIT` pipeline state between `dda_core.sv`'s `INIT` and `PREP` states to
register the multiply/subtract result one cycle before the abs/compare/mux consumes it. Costs
1 extra cycle per column (invisible at the frame level: ~90-cycle MARCH loop dominates).
Full writeup: `docs/decisions/soc_top.md`, "dda_core.sv direction pipeline split".

**Verified:** Verilator lint clean (no warnings near the edit), sim regression still 80/80 +
80/80 PASS (cycle count 16170→16190, latency-only), full Vivado impl re-run: **WNS
+0.020ns → +0.180ns (9x improvement)**, 0 errors, 0 critical warnings, bitstream regenerated.
New critical path is now the per-core `fpdiv` (wall-height divider), matching what this
handoff's Known Issues section already predicted as the next timing lever — margin is healthy
again so no immediate action needed there.

**Still not reflashed to hardware** — see Known issues below, unchanged.

## Known issues / pending work

### Timing margin — RECOVERED, WNS = +0.180 ns (was +0.020 ns, originally +0.420 ns)
Fixed via the `dda_core.sv` `DIR_WAIT` pipeline split described above — see
`docs/decisions/soc_top.md` for the full root-cause writeup. New critical path is the per-core
`fpdiv` (wall-height divider, 14.873ns/11 logic levels) — margin is healthy for now, but this
is the next thing to pipeline if more GPU logic gets added. 100 MHz was never in reach
regardless — the DDA fixed-point arithmetic needs `fpmul`/`fpdiv` pipelining independent of
anything from either session.

### Unconfirmed on real hardware
Buttons, wall collision, and wall-height rendering have **only** been verified in simulation
and via Vivado place+route — none of it has been physically flashed and tested since
2026-06-13. Re-flash (see Quick rebuild reference) and check each independently.

**UART is not "unconfirmed", it's a known stub** — `rtl/core/uart_lite.sv`'s own header says
so explicitly ("Minimal UART stub... Replace with a full UART... for real FPGA use"): it
accepts AXI writes and acks them, but `tx` is hardwired to idle (`assign tx = 1'b1;`) and `rx`
is unused. Firmware's periodic `frame 0xNNN cycles=0xNNN` debug print is real CPU/AXI activity
but never reaches a physical serial line — nothing will appear on `/dev/ttyUSB0` regardless of
wiring. Needs a real UART core (e.g. Xilinx AXI UART Lite) before serial debug output can work.

### `software/ref/raycaster_ref.py` map drift
Its internal map (procedurally generated rooms) doesn't match the real map used everywhere
else (`gen_map_hex.py`'s `MAP_STR`, also embedded directly in `tb_soc_top.cpp`). Noticed while
building wall-height verification, not fixed — the golden reference string in
`tb_soc_top.cpp` is hardcoded and doesn't depend on this script being live, so it wasn't a
blocker this session. Fix before trusting `raycaster_ref.py` as a live oracle again.
